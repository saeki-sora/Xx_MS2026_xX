## 1. 目標と方針（ユーザー承認済み）

- 4人がそれぞれ別のPC（握力センサー1台ずつ）を持ち寄り、LANで同じ試合を遊ぶ。最大3万体の群衆も同期する。
- プレイヤー1（番号0）のPCがHostを兼ねる。**Host権威**（結果はHostが決め、Clientは入力を送って結果を表示する）。
- 通信は NGO（Netcode for GameObjects）+ D-Drive のネットワーク層。接続は `FortressNetworkBootstrap`（D-Drive の `StartHost/StartClient` を呼ぶ）。
- 同期は、シーンに1つの「[Fortress] NetSync」（NetworkObject）に付けた中継役（`*NetworkHub`）が行う。敵や破壊可能物に NetworkObject は付けない（デザイナーの手間を増やさないため）。
- 本番会場の回線は**有線LAN（スイッチングハブ）**の予定（2026-10-04 回答）。

### ユーザーが決めたこと（作業中に確認した内容）
- 各PCのセンサーは、そのPCでは常にP1（番号0、キーボードならQ）として読む。
- Phase 1〜3の間の当たり判定はHostだけ。自分のレーザーはHost確定のみ（予測なし）。ゲージは自分の分だけ。
- ドロップ品は「未定（今は見た目扱い、各PCで別々に出す）」。
- 群衆は最初「各PCで計算＋Hostで補正」方式だったが、密集するとClientの敵が震えて隙間だらけになるため、2026-10-05に「写真方式」（Hostの写真を先読みして表示）に変更し、補正方式のコードは削除した（ユーザー決定）。
- 握力入力: 実機とキーボードを合成（`CompositeGripTransport`）。デバイスが無いPCでもキーボードで動く。
- 演出（エフェクト・効果音、2026-10-04）: 通信はしない。各PCが「Hostから届いた状態の変化」と「自分のPCでの当たり判定（見た目用）・群衆の計算」を見て自分で鳴らす。レーザーの発射口・着弾点・群衆の敵に当たった瞬間、破壊可能物・スマッシュボールの演出がこの方式。素材はD-Driveの番号札で、VFXの Flags › Net は Local のまま（Cosmeticにすると二重に出る）。群衆ヒットは全レーザー合計で1秒60個まで（PCごとに数える）。

段階5の設計（2026-10-05、ユーザー決定: 優先する敵は4種類すべて／通信量は今と同程度／速度は作って比べて決める）:
- Hostは、つながっているClientごとに、敵1体ずつ「補正の必要度」を毎フレーム貯める。貯まる速さ = 大事さ ×（ズレの見込み＋0.25）。
  - 大事さ = 1 ＋ そのClientの画面（＋余白3）に映っている 3 ＋ レーザーの近く 4 ＋ コアの近く 2。
  - ズレの見込み = 前回送った位置と速度から予想した位置と、今の位置の差（押し合いで急に動いた敵ほど大きい）。
- 毎フレーム、通信量の枠に収まる数だけ、貯まった順に送る。同じ敵は0.05秒に1回まで。1秒送っていない敵は必ず先に送る（画面外の敵も1秒以内に補正される）。
- 通信量の枠（Client1人あたり）: 普段720KB/秒（段階4の0.25秒間隔と同じ量）、ズレが大きい間は最大1800KB/秒。往復時間が一番良かった値より25ms以上伸びたら回線が混んでいるとみなして0.7倍に下げ、戻ったら少しずつ上げる（下限120KB/秒）。
- Clientは0.5秒ごとに、ズレと一緒に自分の画面の範囲をHostへ送る。先読みには往復時間の半分を足す。
- 比較用に、従来の方式（番号順に全員を同じ間隔で送る）にも起動引数で戻せる（`-fortress-swarm-priority 0`）。速度つき（1体6→10バイト）は `-fortress-swarm-velocity 1`。
- 計測には「Clientの画面に映っている敵だけのズレ」（ログの `errView`）を追加。

段階5の1回目の計測（2026-10-05、1台2起動）で分かったこと → 直して再ビルド待ち（段階5b）:
- ゲームのシーンには視点の部品（FortressCameraRig）が無く、メインカメラだけだった → 「画面内」が判定できていなかった。カメラの四隅から見える範囲を求める方式に変更。
- NGOの往復時間（RTT）にはフレーム時間も含まれる。一斉投入でHostのFPSが430→90に落ちただけでRTTが1→10〜26msに伸び、「回線が混んだ」と誤判定して投入直後に通信量を下げていた（投入後2秒のズレ: 従来2.8 → 優先度つき4.3）。RTTを0.5秒でならし、基準を早めに忘れ、判定の幅を25→40msに。

- 1回目の参考値（投入5〜30秒後、errAvg）: 従来 0.405（626KB/秒）／優先度つき 0.419（934KB/秒）／速度つき 0.426（940KB/秒）。偏りがあるので正式な比較は段階5bで。

- 優先度つきは、投入直後（0〜5秒）のズレが従来より約2割小さく、**画面内は約2.5〜3割小さい**。通信量をそろえても効果はほぼ同じ。落ち着いた後（5秒〜）は全体のズレは変わらず、画面内がわずかに小さい。
- 速度つきは画面内のズレがさらに小さい（2〜5秒で約2割）が、2〜5秒に「瞬間移動」が数百回出る（速度なしはほぼ0）。目に見える飛びの方が目立つので、**既定は速度なしのまま**。原因（Hostの速度を引き継ぐことか、先読みに使うことか）の切り分けは今後の宿題。
- 回線の混雑の誤判定は起きなくなった（下げた回数0、RTT 13〜24ms）。
- 普段の通信量: 既定（優先度つき）は約880KB/秒で、従来（約620KB/秒、敵が2.5万体に減ると従来は減る）より多い。Clientのズレ（約0.4）が「少ない」の基準0.3を上回るので、普段の量（720）より少し上で落ち着くため。有線LANなら問題ない量（Client1人あたり約7Mbps）。

段階6（写真方式）の経緯と設計（2026-10-05）:
- ユーザー報告: bench_2pで見ると、Hostは密集して流体のように動くのに、Clientは隙間だらけで、敵が1体ずつガクガク震える。
- 原因: 補正方式は、Clientが自分で計算した位置とHostの位置を、敵ごとにばらばらの時刻に混ぜる。密集した群衆ではズレ（平均約0.4）が敵1体分の間隔とほぼ同じなので、Hostの位置へ移した敵が隣と重なり、押し合いの計算で両方が弾ける → 全体が震え、弾けた分だけ隙間ができる。補正の量や優先度では消えない（方式の限界）。
- 検討した案: (1) 写真を2枚待ってその間をつなぐ（震えは消えるが0.1〜0.15秒遅れる）、(2) 全PCで同じ計算をする（ロックステップ。BurstはCPUの種類で小数の結果が変わり得て、3万体の押し合いでは小さな差がすぐ大きなずれに育つので危険）。→ ユーザーが「遅れも震えもない案」を希望し、(3) を採用。
- (3) 写真方式: 全員が同じ瞬間の位置なので重ならない。写真を待たずに最新の写真を速度で先へ進めて表示するので、遅れは通信時間（LANで数ミリ秒）だけ。群衆は滑らかに流れるので「前の2枚から予想した位置との差」はごく小さく、1体あたり約1バイトに縮む見込み（普段の通信量は補正方式と同程度）。出現・消滅も写真に入れるので顔ぶれもずれない。HostとClientで1単位でも予想が食い違うとずっとずれるので、予想は整数だけで計算し、毎回の確かめ用の値が合わなければ全員分の写真で立て直す（立て直し回数はログの `resyncs`、0であるべき）。
- 注意: 確実な届け方（取りこぼしたら再送）を使う。NGOの確実な届け方は1接続あたり約2.7MB/秒が上限。途中参加のときの全員分の写真は3万体で約540KB。

## 4. 宿題: 2台のPCでのテスト（ユーザーが別の機会に実施）

1台のPCで複数起動すると本番より重く出るため、実際の重さ・遅れは2台で測る必要がある。

準備
1. 両方のPCに同じビルドを置く（`Builds\TestBuild` をフォルダごとコピー。**必ず同じビルド**。違うと破壊可能物・敵の並びの照合でエラーになり同期しない）。
2. Host側PCのIPアドレスを調べる（コマンドプロンプトで `ipconfig` → IPv4 アドレス）。
3. 初回起動時にWindowsのファイアウォールの確認が出たら「プライベート ネットワーク」を許可する（UDP 7777 を使う）。
4. 両方のPCでプロジェクトの `Tools\NetTest\` を使う（またはbatを `MS2026.exe` のフォルダと一緒にコピーし、環境変数 `MS2026_BUILD_DIR` でビルドの場所を指定）。

動作確認
- Host側PC: `run_instance.bat host 0`
- Client側PC: `run_instance.bat client 1 <HostのIP>`

負荷計測（2台）
- Host側PC: `run_instance.bat host 0 - -fortress-bench -fortress-bench-burst 30000 -fortress-bench-clients 1 -fortress-bench-quit 60 -fortress-bench-no-wave`
- Client側PC: `run_instance.bat client 1 <HostのIP> -fortress-bench -fortress-bench-quit 60 -fortress-bench-no-wave`

## 5. 既知の制限・注意

- コアHPはHostでしか減らない（Phase 5で同期）。勝敗・ラウンド進行は未実装。
- Host離脱時の引き継ぎは未実装（Phase 6）。今はHostが落ちると全員切断される。
- 群衆の写真は確実な届け方（取りこぼすと再送）で送る。取りこぼしの多い回線（混んだWi-Fiなど）では一瞬引っかかることがある。1台のPCで4つ起動すると、投入直後に裏のClientがCPU不足で乱れる（実機4台での確認が必要）。
- 破壊可能物・敵の種類は「ウェーブ設定に入っている物」「シーン内の名前の並び」で番号を振る。HostとClientは必ず同じビルドを使う。
- 要塞デザイナーのテストボタン（壊す・湧かせる・ストレステスト）はHost側で押す（Clientでは無効）。

## 5b. タイトル → ロビー → ゲーム（2026-10-08）

ユーザー決定: 「ロビーで接続して全員待つ」形（ロビーのシーンでつながり、全員そろったらホストの「ゲーム開始」で全員一緒にゲームへ）／開始は「全員が準備OKなら押せる」（ホストは「待たずに開始」もできる）／ビルドの最初のシーンはタイトル。詳しい仕組みは `Docs/Tools/UIStudio_AI_Reference.md` の 7章、人間向けは `UIStudio_ガイド.html` の「タイトル → ロビー → ゲーム」。

- 流れ: Title → **Lobby**（名前・P1〜P4を選ぶ → 部屋を作る／同じLANの部屋を一覧から選んで参加）→ 部屋（全員の名前・準備OK・通信の遅れが全員に見える。握り続けても準備OK）→ ホストの「ゲーム開始！」→ 3・2・1 → 全員でゲームへ。試合中は Esc の一時メニューで「全員でロビーに戻る（ホスト）」「試合から抜ける（参加側）」「タイトルへ」。
- 仕組み: **ロビーのシーンは遊んでいる間も読み込まれたまま**。通信の土台（NetworkManager・D-Drive・FortressNetworkBootstrap・NgoNetBridge・センサー）はロビーのシーンにあり、ホストが NGO のシーン管理でゲームのシーンを**重ねて（Additive）**読み込む。参加側は `SetClientSynchronizationMode(Additive)` により、後から参加した人もロビーのシーンはそのまま使い、ゲームのシーンだけ読み込む。各中継役（*NetworkHub）は OnNetworkSpawn で準備するので、ロビーで先につながっていても問題ない。
- ゲームのシーンの同じ物（通信の土台・[UI]・EventSystem・センサー）は、ロビーから来たときだけ `[Session] Guard`（`GameSceneSessionGuard`）が動き出す前に外す。**ゲームのシーンだけで Play／起動すれば今まで通り**（接続UI・起動引数もそのまま）。
- **テスト用の bat は変更なしで使える**: `-fortress-` で始まる引数があると、タイトルがロビーを飛ばしてすぐゲームのシーンを読み込む（今までと同じ流れ）。
- ロビーのやり取りは NGO の名前つきメッセージ（`MS2026.Lobby.Hello/Ready/State`）。ホストが部屋の一覧（席・名前・準備OK・ホストか・遅れ）を変わるたびに全員へ配る。**これで「参加側には他の人の接続状況が届かない」問題は、ロビーから来た場合は解消**（`player.N.connected` も全員のPCで正しい）。ゲームのシーンには NetworkObject を増やしていない。
- 部屋さがし: UDP **47777** のブロードキャスト（ホストが返事をする）。ゲームの通信（UDP 7777）とは別。初回にファイアウォールの許可が要る。見つからなくてもアドレス入力で参加できる。違うビルドは一覧に「ビルドが違います」と出る（`Application.version` で判定）。
- 確認済み（1台のエディタ、ホストのみ）: 部屋を作る・部屋さがしの返事・準備OK・3・2・1・ゲームを重ねて読み込む（2回）・番人が重複を外す（NetworkManager/D-Drive/UI/EventSystem/センサーが各1つ）・全員でロビーに戻る・接続の時間切れのお知らせ・タイトルへ戻る→もう一度ロビー。
- **宿題（未確認）**: 2台以上での参加側の流れ（一覧から参加・途中参加・準備OKの同期・カウントダウン・全員でゲームへ／ロビーへ・ホストが抜けたときのお知らせ・外す）。ビルドして 2台で確かめる。1台で試すときは、ロビーで「部屋を作る」と「このアドレスに参加（127.0.0.1）」を別々の起動で行う（タイトルからの通常の起動。bat は使わない）。
