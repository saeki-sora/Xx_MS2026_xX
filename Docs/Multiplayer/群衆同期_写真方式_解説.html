    SNAPSHOT写真方式

    「握れ、灼ける前に」の群衆を全員の画面にそろえる仕組み — Snapshot Replication + Delta Coding + Extrapolation

    Hostが全員の位置を同じ瞬間に撮った写真を、
    前の写真との差だけに縮めて1秒30回配り、
    Clientは少し先を予想して表示する。

    たとえるなら「パラパラ漫画を1秒に30ページ、前のページとの違いだけメモして郵送する」仕組み。受け取った人は、次のページが届くまでの一瞬を「みんな同じ向きにちょっと進めて」描いておくので、遅れも見えないし、絵がガタガタもしない。

    何のため
    最大3万体の敵の群れを、4台のPCで「同じ見た目」に保つ
    一般的な名前
    スナップショット同期 ＋ 差分（予測）符号化 ＋ 推測航法（外挿）
    結果
    ズレ 約0.04（敵の半径0.22の1/5以下）、Client1人あたり普段 約0.6MB/秒、震え・隙間なし
    導入難易度
    ★★★★★ 上級（理由はこちら）

    第1部　全体像 — 何を、どうやって、どれくらい

    専門知識なしで読めます。

    01 / Overview

    ひとことで言うと、Hostの写真を配る

    このゲームのネット対戦では、Host（部屋を立てたPC）だけが本物の計算をします。敵がどこに湧き、どう歩き、誰のレーザーで倒れたか。全部 Host が決めます。他の3台（Client）は、Host から届く「写真」を見て、同じ景色を描きます。

    1枚の写真が届くまで（1秒に30回くり返す）
    HOST
    ① 計算する
    3万体の歩き・押し合い・被弾をいつも通り計算
    HOST
    ② 撮る
    全員の位置を同じ瞬間に記録
    HOST
    ③ 縮める
    前の2枚からの予想との差だけを、数ビットに詰める
    LAN
    ④ 届ける
    確実に・順番どおりに（数ミリ秒）
    CLIENT
    ⑤ 戻す
    同じ予想に差を足して位置を復元。Hostと1ビットも違わない
    CLIENT
    ⑥ 先読みして描く
    届くまでの遅れの分だけ、各敵の速度で少し先へ進めて表示
    📸

    同じ瞬間の写真だから、震えない

    全員の位置が「同じ瞬間」のものなので、隣どうしがぶつからない。以前の方式で起きていた「ガクガク震えて隙間だらけ」が、原理的に起きない。

    例：密集して流体のように動く群れが、Clientでもそのまま見える
    🗜️

    差だけ送るから、軽い

    群衆は滑らかに流れるので、「前の2枚から予想した位置」と実際の位置の差はほぼ0。それを可変長の符号で詰めると、1体あたり約7ビット。

    例：そのまま送ると 約43Mbps → 実際は 約5Mbps
    🔮

    先読みするから、遅れない

    写真を待ってから描くと遅れる。そこで最新の写真を「各敵の速度 × 届くまでの時間」だけ先へ進めて描く。遅れは実質、通信の時間（LANで数ミリ秒）だけ。

    例：外れても平均 0.04（1ピクセルは約0.026）
    02 / Names

    「写真方式」はあだ名。正式には3つの技術の組み合わせ

    このプロジェクトでは分かりやすさのため「写真方式」と呼んでいます。ゲーム業界・通信の世界では、次の名前で知られる技術を組み合わせたものです。

    使っている技術と、世間での呼び名
    この文書での呼び方一般的な名前（英語）何をする身近な例
    写真を配るSnapshot Replication（スナップショット同期・状態同期）ある瞬間の「状態そのもの」を定期的に送るオンラインFPS（Valveのゲームなど）の基本形
    予想との差だけ送るDelta Compression / Predictive Coding（差分圧縮・予測符号化）前の値から予想し、外れた分だけ送る動画（MPEGの「前のコマとの差」）、音声圧縮
    ビットに詰めるExp-Golomb Coding（指数ゴロム符号）＋ ZigZag小さい数ほど短い符号にするH.264/H.265 動画の中で実際に使われている符号
    先読みして描くDead Reckoning / Extrapolation（推測航法・外挿）最後に分かった位置と速度から「今」を予想する船や飛行機の航法、多くのオンラインゲーム
    外れを見た目で隠すError Smoothing / Visual Offset（誤差の平滑化）予想の外れを一瞬で直さず、数フレームかけて消すレースゲームの他車の表示
    全員分の写真Keyframe（キーフレーム、I-frame）差ではなく「全部」を送る1枚。途中参加・立て直しに使う動画の「キーフレーム」と全く同じ考え方
    !
    よくある「スナップショット補間（Snapshot Interpolation）」は、届いた2枚の間をつなぐので、必ず写真1〜2枚分（このゲームなら0.03〜0.1秒）遅れます。今回は2枚を待たずに最新の1枚から先を予想する（外挿）ので遅れません。代わりに「予想が外れる」問題が出るので、それを目立たせない工夫を第2部で説明します。
    03 / Difficulty

    導入難易度は 上級（★4つ）

    やっていること自体は「写真を撮って、差を送って、先読みする」だけです。難しいのは細部を1ビットも間違えられないところと、時間の扱いです。部品ごとの難しさは次のとおりです。

    部品ごとの難しさ ★の数は「ネットワークの基礎がある人」にとっての難しさの目安
    部品難しさなぜ難しい
    写真の圧縮・復元★★★★★HostとClientの計算が1単位でも違うと、その後ずっとずれ続ける（しかも気付きにくい）。小数の計算はCPUによって結果がわずかに変わり得るので、予想は全部整数で書き、さらに毎回「確かめ用の値」で照合した。ビット単位の読み書き（ビットパッキング）も、1つ間違えると以降が全部壊れる。
    時計合わせと先読み★★★★★HostとClientの時計は別物。「今、Hostでは何時か」を、届いた写真の時刻から推定する必要がある。届く時間は毎回ばらつくので、その揺れが表示の揺れにならないようにする。
    外れを隠す表示★★★★★「計算上の位置」と「描く位置」を分けて持ち、差を数フレームで消す。考え方は単純だが、新しく湧いた敵・消えた敵・瞬間移動が必要な場合との組み合わせに注意が要る。
    途中参加・立て直し★★★★★「差」の流れの途中から入る人に、どの時点から差を受け取ればよいかを矛盾なく伝える（キーフレームの直後から）。
    遅れたら軽くする★★★★★仕組みは簡単。ただし「何を減らすか」を間違えると逆効果（実際に一度失敗した。こちら）。
    計測の仕組み★★★★★「良くなったか」を数字で言えないと改善できない。測り方そのものが偏っていて判断を誤ったこともある。
    ★★★★★

    目安：ネットワークゲームを作ったことがある人なら、仕組みを理解して同じ物を作るのに数週間。初めての人がゼロから作るなら、この文書の第3部の知識を身につけるところから始めて数か月。（あくまで目安です）

    02
    第2部　工夫した点 — なぜそうしたのか

    一つ一つの工夫に「困っていたこと」「やったこと」「効果」があります。たとえ話から入り、最後に少しだけ中身を見せます。

    05 / Same moment

    工夫1　全員を同じ瞬間でそろえる

    これがこの方式を選んだ一番の理由です。以前の方式で起きた問題から説明します。

    以前：各PCで計算＋補正 震える

    Clientも自分で群衆を計算し、Hostから届いた位置で1体ずつ、ばらばらの時刻に直していました。ところがClientの計算はHostと少しずつずれ（平均0.4）、その大きさは敵1体分の間隔とほぼ同じ。直された敵が、まだ直されていない隣の敵に重なり、押し合いの計算で両方が弾け飛ぶ。これが毎秒何万回も起きて、全体がガクガク震え、弾けた分だけ隙間ができていました。

    今：写真方式 震えない

    Clientは群衆を計算しません。全員の位置が「同じ瞬間の写真」から来るので、Hostで重なっていない敵は、Clientでも重なりません。先読みも全員が同じ時間だけ、それぞれの速度で進むので、流れに沿って一緒に動き、ぶつからない。

    見比べてみる（イメージ）
    以前1体ずつばらばらに直す
    今同じ瞬間の写真＋先読み

    実際のゲームの映像ではなく、仕組みを見せるための簡単な再現です。左は「計算のずれ」と「ばらばらの補正」で点が震え、ぶつかって隙間ができます。右は全員が同じ流れで動きます。

    !
    教訓：補正の頻度を上げる・大事な敵から直す（優先度）など、以前の方式のままでも多くの改善を試しました。数字は良くなっても、「別々の計算結果を混ぜる」限り震えは消えませんでした。方式そのものの限界は、細かい調整では越えられません。
    06 / Prediction

    工夫2　予想との差だけを送る

    写真を1秒30回、全員分そのまま送ると、3万体 × 位置4バイト（＋番号2バイト）× 30回 ＝ 毎秒5.4MB（約43Mbps）。1人分としても重く、4人なら3倍です。そこで「当たり前のこと」は送らないことにしました。

    群衆は滑らかに流れるので、「前の2枚から、同じ速さで進んだら」という予想はほとんど当たる。外れた分（たいてい0〜数単位）だけを送る。

    たとえ話

    毎朝同じ時刻に同じ道を通る人の「今日の通勤」を報告するとき、「いつも通り」なら一言で済みます。いつもと違ったところ（「信号で3秒待った」）だけ伝えれば十分です。

    どれくらい小さくなる？

    敵は1秒に約2進むので、1/30秒で約0.067。位置の単位（1/500）だと約33単位の移動です。そのまま送ると1軸10ビット前後。予想との差なら、ほとんどが0〜2単位で、1〜3ビット程度になります。

    i
    写真の間隔は毎回ぴったり1/30秒ではありません（Hostのフレームの都合で数ミリ秒揺れる）。そこで「前回の間隔に対して今回は何倍か」も一緒に送り、予想をその分だけ伸び縮みさせています（ratioQ）。
    07 / Entropy coding

    工夫3　小さい数を短い符号で書く

    差はほとんど0や1なのに、いつも32ビット（int）で送ったら台無しです。そこで「小さい数ほど短く、大きい数でも書ける」符号を使います。指数ゴロム符号です。

    1. ZigZag：差はマイナスもあるので、0, −1, 1, −2, 2 … を 0, 1, 2, 3, 4 … に並べ替える（小さい数のまま）。
    2. 指数ゴロム符号：その数を「0の並び＋1＋残りのビット」で書く。0の数で長さが分かるので、区切り記号がいらない。
    3. 次数 k：差が全体的に大きめの写真では、最初から下位kビットを素直に書いた方が短い。そこで写真1枚ごと・x軸とy軸ごとに、合計が一番短くなるkを0〜7から選んで、写真に書いておく。
    やってみる：差を符号にする（説明用に、教科書どおり上位ビットから並べています）
    ZigZag後の値
    6
    ビット数
    5
    int のままなら
    32
    長さを表す0の並び区切りの1値の残りのビット

    結果、落ち着いているとき1体あたり約7ビット（x・y合計）まで縮みました。そのまま送る場合（番号2バイト＋位置4バイト＝48ビット）の約1/7です。

    08 / Quantization

    工夫4　見えない細かさは捨てる、でも誤差は溜めない

    位置は1/500単位（0.002）で持っていました。でも画面の1ピクセルは約0.026。0.002の違いは目に見えません。そこで差を4単位（0.008、約1/3ピクセル）刻みに丸めて送ります。1軸あたり約2ビット軽くなり、普段の通信量は約1/3減りました。

    ふつうに丸めると…ずれが溜まる

    毎回「本当の位置」を基準に丸めた差を送ると、Clientは「丸めた差」を積み重ねていくので、丸めの誤差が少しずつ溜まって、どんどんずれていきます。

    この方式 溜まらない

    Hostは「Clientが復元するはずの位置（丸めた後）」を自分でも計算し、それを次の予想の元にします。毎回の差は「Clientが今持っている位置」との差になるので、誤差はいつも半刻み（0.004）以内に収まり、溜まりません。

    i
    これは音声・画像圧縮で「閉ループ予測（closed-loop prediction）」と呼ばれる定番の工夫です。「送り手が受け手の頭の中を再現しながら送る」と覚えてください。
    09 / Bit-exact

    工夫5　HostとClientで1ビットも狂わせない

    差だけを送る方式には、大きな弱点があります。Clientが一度でも違う値を復元すると、その後の予想も全部ずれ、ずっと戻らないことです。そこで3重に守っています。

    🔢

    整数だけで予想する

    小数（float）の計算は、CPUの種類や命令の選び方で最後の桁が変わることがあります。予想の計算は全部整数で行い、間隔の比も「1024倍した整数」にしてHostが送ります。

    例：Predict = h1 + ((h1−h2) × ratioQ + 512) >> 10
    🧾

    確かめ用の値で照合

    Hostは全員の位置から「確かめ用の値（チェックサム）」を計算して写真に入れます。Clientも復元後に同じ計算をし、合わなければ壊れたと判断します。

    記録：今までの計測で 不一致 0回
    🛟

    壊れたら全員分で立て直す

    照合が合わない・写真の番号が飛んだときは、Hostに「全員分の写真（キーフレーム）」を頼み、そこから差の受け取りをやり直します。

    途中参加も同じ仕組みで入る
    !
    なぜ「確実に届く送り方」なのか：差は「前の写真」を前提にしているので、1枚でも抜けると次から復元できません。だから写真は、取りこぼしたら再送してくれる送り方（Reliable）で、順番どおりに届けています。代わりに、取りこぼしの多い回線では再送待ちで一瞬引っかかることがあります（有線LAN前提の判断）。
    10 / Extrapolation

    工夫6　写真を待たずに先を予想して描く

    写真は「撮った瞬間」の景色です。Clientに届いたときには、もう少し時間が経っています。そこでClientは「Hostでは今ごろこうなっているはず」の位置に描きます。

    先読みの量は、写真が届いた直後は短く（数ミリ秒）、次の写真の直前は長く（約40ミリ秒）なる。届く時間の揺れに引きずられないよう、時計の差の推定を工夫している（下）。

    「Hostでは今何時？」の推定

    写真には撮った時刻（Hostの時計）が書いてあります。Clientは「届いた自分の時刻 − 撮った時刻」を毎回計算し、一番小さかった値を「時計の差」の基準にします。一番速く届いた回が、一番余計な遅れの少ない回だからです。基準は1秒に2ミリ秒ずつ忘れていき、回線の状態が変わっても合わせ直します。

    速度はどこから？

    速度は送っていません。「1枚前との位置の差 ÷ 時間」で分かります。これも全員が同じ写真から計算するので、隣どうしの速度もそろい、先読みしてもぶつかりません。ただし写真が途切れたときに飛んでいかないよう、先読みは最大0.2秒までにしています。

    11 / Smoothing

    工夫7　先読みの外れは見た目だけでゆっくり消す

    先読みは予想なので、新しい写真が届くと少し外れていたことが分かります（平均0.04）。それを一瞬で直すと、敵がピクッと跳ねて見えます。

    新しい写真が届く
    →
    位置（計算上）はすぐ正しい所へ
    →
    描く位置は前のフレームの続きから
    →
    その差（ずらし）を約0.07秒で消していく

    「計算上の位置」と「描くためのずらし」を分けて持つのがポイントです。計算上の位置はいつも正しいので、ずれが溜まりません。ずらしは見た目だけなので、当たり判定などには影響しません（そもそも当たり判定はHostだけが行います）。外れが2以上と大きすぎるときは、滑らせると不自然なので、その場で合わせます（＝「瞬間移動」の回数として数えています）。

    12 / Burst

    工夫8　一斉投入の混乱期には速度に上限

    3万体を一度に湧かせると、Hostでは最初の1秒、狭い所で押し合って敵が弾け飛びます。このとき写真の差から計算した速度が、敵の本来の最高速度よりずっと大きくなり、先読みが行き過ぎていました（1秒目の瞬間移動が約6万回）。

    ✓
    先読みに使う速度を「その敵の種類の最高速度 × 1.6」までに抑えました（Hostの計算でも同じ上限を使っている）。1秒目の瞬間移動は 約6万 → 約3,500回（約94%減）、2秒目以降はほぼ0になりました。
    13 / Adaptive quality

    工夫9　遅れたら枚数ではなく細かさを減らす

    確実に届ける送り方には「1度に送れる量」に上限があります。一斉投入の直後は写真1枚が重くなり（約60KB）、4人分を1台のPCで動かしたテストでは、裏のClientに写真が最大0.2秒遅れて届きました。そこで「遅れているときは写真を軽くする」仕組みを入れました。

    最初の案：写真の枚数を減らす 逆効果

    遅れは減りました（0.2秒→0.1秒）。でも写真の間隔が0.1秒に延びたせいで、混乱期の不規則な動きを0.1秒も先読みすることになり、瞬間移動が約1万→約11万回に増えました。遅れていなかったClientまで悪化しました。

    今の案：位置を少し粗くする 採用

    枚数（1秒30枚）はそのままにして、遅れている間だけ位置の細かさを 0.008 → 0.016 → 0.032（約1ピクセル）と粗くし、写真を軽くします。間隔が変わらないので先読みの精度は保たれます。

    自動調整のルール
    状況判定やること
    写真がいつもより80ms以上遅れて届いた（一番遅いClient）送りきれていない細かさを1段粗くする（0.3秒に1回まで、最大2段）
    遅れが40ms以下の状態が1秒続いた落ち着いた1段戻す
    その間様子見今のまま
    !
    教訓：「通信が詰まったら送る量を減らす」は正しいのですが、何を減らすかで結果が真逆になりました。このゲームでは「時間の細かさ（枚数）」は先読みの精度そのものなので削れず、「位置の細かさ」は目に見えないので削れる、という違いがありました。
    14 / Join & membership

    工夫10　途中参加と、敵の出入りも同じ写真で

    🚪

    途中参加

    参加したClientは「全員分の写真（キーフレーム）」を頼みます。Hostは次の写真を撮った直後に、そのClientにだけ全員分（3万体で約540KB）を送り、それ以降の差の写真を送り始めます。同じ順番どおりの送り方なので、「全員分」の後に「差」が必ず届き、矛盾しません。

    計測：3万体の戦場に4人目が入って、1秒以内に約2.4万体を受け取り、ずれ0.05で追従
    🧩

    湧いた・消えた

    写真には「消えた敵（理由つき：倒された・コアに着いた）」「新しく出た敵（種類・位置・向き）」も入っています。位置と顔ぶれが同じ1枚で届くので、「位置は届いたのに、その敵をまだ知らない」というずれが起きません。

    注意：同じ番号で消えてすぐ出直した敵は、消さずにそのまま使う（同じフレームで消す処理と出す処理が重なると両方消えるため）
    15 / Performance

    工夫11　速く、そしてゴミを出さない

    ⚡

    Burst と Jobs

    写真の作成・復元・先読みは、Unity の Burst（C#を高速な機械語にする仕組み）で動かします。3万体分でも1ミリ秒もかかりません。

    🧹

    GC（ゴミ集め）を起こさない

    C#では、使い終わったメモリを集める「GC」が走ると一瞬止まります。送受信は「名前なしメッセージ」と一時メモリ（Allocator.Temp）で行い、毎フレームのゴミを出しません。

    🪶

    Clientは計算しない

    Clientは押し合いの計算をやめたので軽くなりました（FPS 257→330）。Hostも以前の補正のための計算がなくなり、113→160FPSになりました。

    03
    第3部　ネットワークの基礎講座 — ゼロから一人前へ

    「パケットって何？」から始めて、ゲームの同期方式を自分で選び、測って直せるところまで。第1〜2部に出てきた言葉は、ここで全部説明します。各講の最後の「ここだけ覚える」だけ拾い読みしても大丈夫です。

    L1 / Basics

    ネットワークは小包の郵便

    LEVEL 1

    PCどうしの通信は、電話のように線がつながりっぱなしになるのではありません。データを小さな小包（パケット）に分けて、宛先を書いて、次々に送り出す「郵便」です。

    📦

    パケット

    データの小包。1個に入るのは約1,500バイトまで（これをMTUと呼ぶ）。大きいデータは複数の小包に分けて送り、向こうで組み立て直す。

    🏠

    IPアドレス

    PCの住所。例：192.168.1.10。家やLANの中だけで通じる住所（プライベート）と、インターネット全体で通じる住所がある。

    🚪

    ポート

    住所の中の「部屋番号」。同じPCでも、ゲームは7777番、ブラウザは別の番号…と使い分ける。このゲームはUDPの7777番。

    🛣️

    LAN とインターネット

    LANは同じ建物の中の道（スイッチやルーターでつながる）。インターネットは国中・世界中の道。LANは近いので速く、混みにくい。

    ★
    ここだけ覚える：データは小包（パケット、約1,500バイトまで）に分けて送る。宛先は「IPアドレス（住所）＋ポート（部屋番号）」。
    L2 / Bandwidth & latency

    「速い」には2種類ある

    LEVEL 1

    ネットワークの「速さ」は、道の太さ（帯域）と届くまでの時間（遅延）の2つに分けて考えます。混ぜると判断を誤ります。

    ネットワークの大事な5つの数
    名前意味たとえ単位・目安
    帯域（バンド幅）1秒に運べる量道路の車線の数Mbps（メガビット毎秒）。有線LANは100〜1000Mbps
    遅延（レイテンシ）1個の小包が届くまでの時間家から郵便局までの距離ミリ秒（ms）。LAN内は1ms未満
    RTT（往復時間）送って、返事が戻るまで行って帰ってくる時間ms。片道の約2倍
    ジッター遅延の「ばらつき」渋滞で到着時刻がぶれるms。小さいほど安定
    パケットロス途中で消える小包の割合郵便事故%。有線LANではほぼ0、混んだWi-Fiでは数%

    ビットとバイトに注意

    1バイト＝8ビット。回線の速さは「ビット」（Mbps）、ファイルの大きさは「バイト」（MB）で言うことが多い。1MB/秒 ＝ 8Mbps。この文書の「Client1人あたり0.6MB/秒」は約5Mbps です。

    遅延の目安

    同じLAN：1ms未満 ／ 同じ県内のネット：5〜20ms ／ 日本〜アメリカ：100ms以上。光でも地球の裏まで約70ms かかるので、遠いと絶対に速くできない。だからこのゲームはLAN前提です。

    L3 / TCP vs UDP

    書留のTCP、はがきのUDP

    LEVEL 2

    小包の送り方（プロトコル）には大きく2つあります。ゲームではほぼ必ずUDPを使い、その上に自分たちで「必要な所だけ確実にする」仕組みを作ります。

    TCP（書留郵便）

    • 必ず届く・順番どおりに届く
    • 1個でも抜けると、後ろの小包が全部待たされる（Head-of-line blocking）
    • Webページ、ファイル転送向き

    UDP（はがき）

    • 届くかも順番も保証なし。その代わり待たない
    • 古い情報は捨ててよいゲーム（位置など）に向く
    • 必要なら「届いたら返事」を自分で作る

    このゲームの通信部品（Unity Transport）は全部UDPの上に作られていて、送るたびに「確実に（Reliable）」か「届かなくてよい（Unreliable）」かを選べます。写真方式の写真は、差の積み重ねなのでReliableを選んでいます（工夫5）。

    ★
    ここだけ覚える：確実に届けると、抜けたときに後ろが待たされる。だから「抜けたら困るもの」だけ確実にし、「次が来れば要らないもの」は届かなくてよい送り方にする。
    L4 / Reliability

    「確実に届ける」の中身と限界

    LEVEL 2

    確実な送り方は、ざっくり言うと「番号をつけて送る → 受け取った側が受け取りました（ACK）と返す → 返事が来なければ送り直す」です。

    • 連番（シーケンス番号）：小包に1, 2, 3…と番号を振る。抜けや順番の入れ替わりが分かる。
    • ACK：受け取った番号を相手に伝える返事。
    • 再送：一定時間ACKが来なければもう一度送る。
    • 送信窓（ウィンドウ）：ACKを待たずに「先に送ってよい数」。Unity Transport では最大64パケット。
    !
    このゲームで実際に効いた話：RTTには「相手がパケットを処理するまでの待ち時間（フレームの長さ）」も含まれます。1台のPCで4つ動かすとフレームが遅くなってRTTが延び、送れる量が減って、一斉投入直後に写真が遅れました（工夫9）。回線ではなくPCの重さで通信が遅くなることがあります。
    ★
    ここだけ覚える：確実な送り方の速さの上限は「窓の大きさ ÷ 往復時間」。往復時間は回線だけでなくPCの重さでも延びる。
    L5 / Topology & authority

    つなぎ方と「誰が正しいか」

    LEVEL 2
    🕸️

    P2P（全員どうし）

    全員が全員とつながる。サーバーが要らないが、人数が増えると線が増え、「誰の結果が正しいか」が決めにくい。

    🏢

    専用サーバー

    遊ばない専用のPCが全部計算する。公平で強いが、サーバーを用意する手間とお金がかかる。

    🏠

    Host（このゲーム）

    プレイヤーの1人のPCがサーバーも兼ねる（listen server）。LANのパーティーゲーム向き。Hostが落ちると全員切れる（引き継ぎは今後の課題）。

    権威（Authority）とは「最終的にどの結果を正しいとするか」を決める役のこと。このゲームは Host権威：当たり判定・敵の生死・コアのダメージは全部Hostが決め、Clientはそれに従います。Clientが勝手に「倒した」と決められないので、ずれやズルが起きにくくなります。

    ★
    ここだけ覚える：同期の設計は「誰が正しいか（権威）」を最初に決めるところから。このゲームは Host が正しい。
    L6 / Replication strategies

    同期の方式の地図

    LEVEL 3

    「全員の画面を同じにする」やり方は、大きく5つあります。どれにも得意・不得意があり、ゲームの性質で選びます。

    主な同期方式の比較
    方式送る物見た目の遅れ通信量弱点向いているゲーム
    ロックステップ入力だけ（ボタン・握力など）入力が全員分そろうまでとても少ない全PCの計算が完全に同じでないと破綻。1人が遅いと全員待つRTS、格闘ゲーム
    スナップショット補間状態（写真）写真1〜2枚分＋通信多い（圧縮で減らす）必ず少し遅れるFPS、アクション全般
    クライアント予測＋サーバー補正入力と状態自分の操作は遅れない中予測が外れると巻き戻しが必要で複雑FPSの自分のキャラ
    各自計算＋補正（以前の群衆）ときどき正しい位置ほぼ無し少ないずれる。密集物では混ぜると震える少数の、ぶつからない物
    スナップショット＋外挿（今の群衆）状態（差分圧縮）通信の時間だけ中（圧縮で約1/9）予想が外れる瞬間がある（見た目で隠す）。確実に届ける必要大量の物が滑らかに動く場面

    なぜロックステップにしなかった？

    通信は一番少なくて済みます。でも3万体の押し合いでは、小数の計算のほんのわずかな違い（CPUの種類で起こり得る）が、すぐに大きなずれに育ちます（カオス）。会場のPCが全部同じ機種とは限らないので、危険と判断しました。

    なぜ補間にしなかった？

    補間（2枚の間をつなぐ）は一番安全で滑らかです。ただし写真1〜2枚分（0.03〜0.1秒）必ず遅れます。ユーザーの「遅れも震えもない方法」という希望に合わせ、外挿＋見た目の平滑化を選びました。

    ★
    ここだけ覚える：「入力を送る（ロックステップ）」か「状態を送る（スナップショット）」かが最初の分かれ道。状態を送るなら、次は「待って補間（遅れる・安全）」か「先読みで外挿（遅れない・外れる）」か。
    L7 / Time

    ネットワークゲームは時間のゲーム

    LEVEL 3

    同期で一番やっかいなのは「時間」です。PCごとに時計もフレームの長さも違い、届く時間も毎回ばらつきます。

    • フレーム：画面を1回描く単位。PCが重いと長くなる（60FPSなら約16.7ms）。
    • ティック：通信や計算を一定間隔で区切る単位。このゲームの写真は1秒30回（約33ms）。
    • 時計のずれ：PCの時計は合っていない前提で考える。「相手の時刻」は、届いた情報から推定する。
    • 補間（Interpolation）：2つの分かっている点の間を埋める。安全だが、2点目を待つ分遅れる。
    • 外挿（Extrapolation）：最後の点から先を予想する。遅れないが、外れることがある。
    • ジッターバッファ：届く時間のばらつきを吸収するため、わざと少し待ってから使う仕組み（補間方式で使う）。

    時計の差を推定するコツ（写真方式で使った方法）

    「受け取った自分の時刻 − 相手が送った時刻」は、本当の時計の差に「その回の届くまでの時間」が足された値です。届くまでの時間はいつもプラスで、ばらつきます。だから一番小さかった値が、一番余計な遅れの少ない＝本当の差に一番近い値になります。インターネットの時刻合わせ（NTP）も同じ考え方を使っています。

    ★
    ここだけ覚える：時計は合っていない前提。相手の時刻は「届いた値の最小」で推定する。補間は遅れる・外挿は外れる、の二択を理解しておく。
    L8 / Compression

    データを小さくする4つの道具

    LEVEL 3

    通信量を減らす技は、この順番で考えると整理できます。写真方式は4つ全部を使っています。

    1

    要らない物を送らない

    変わっていない物、相手が自分で計算できる物は送らない。写真方式では「速度」を送らず、Clientが位置の差から計算しています。

    2

    量子化（細かさを決める）

    小数（4バイト）を、必要な細かさの整数（2バイトなど）に変える。0.002刻みで十分なら、それ以上の細かさは捨てる。「目に見えない細かさ」は捨ててよい。

    3

    予測と差分

    前の値から予想して、外れた分だけ送る。当たるほど差は0に近づく。予想を送り手と受け手で完全に同じにするのが鉄則。

    4

    エントロピー符号化

    よく出る値（0付近）を短い符号に、まれな値を長い符号にする。指数ゴロム符号、ハフマン符号、算術符号などがある。「よく出る物を短く」はモールス信号（Eは「・」1つ）と同じ発想。

    i
    圧縮には限界がある：本当に予想できない情報（ランダムな動き）は縮みません。一斉投入直後の混乱期に写真が重くなるのはこのためです（1体約20ビット）。
    ★
    ここだけ覚える：送らない → 細かさを決める → 予想との差にする → 短い符号で書く。
    L9 / Designing reliability

    キーフレームと差分、壊れたら直す

    LEVEL 3

    差分方式は軽い代わりに、1つ狂うと以後全部が狂います。動画と同じく「全部入りの1枚（キーフレーム）」と「差の1枚」を組み合わせ、壊れたことに気付ける仕組みを入れるのが定石です。

    データごとに送り方を選ぶ（このゲームの例）
    データ送り方理由
    群衆の写真（差）Reliable・順番どおり前の写真が前提。1枚でも抜けると復元できない
    全員分の写真（キーフレーム）Reliable・順番どおり以後の差の出発点
    Clientの「遅れ」の報告Unreliable0.25秒ごとに新しい値が来るので、1回抜けても困らない
    握力の入力Unreliable（連番つき）常に最新が大事。古いのは捨てる
    • 連番：写真に番号を振り、飛んだら気付く。
    • チェックサム：中身から計算した「確かめ用の値」を一緒に送り、受け手も計算して比べる。
    • 冪等（べきとう）：同じ物が2回届いても結果が変わらないように作る（例：「出現」が2回届いても2体にしない）。
    ★
    ここだけ覚える：データごとに「抜けたら困るか」で送り方を選ぶ。差分を使うなら、キーフレーム・連番・チェックサムをセットで。

    L11 / Measuring

    L12 / Pitfalls

    実際に踏んだ落とし穴

    LEVEL 4
    Unreliable で大きい配列を送ったら、何も届かなかった
    NGOの「届かなくてよい」送り方は分割されず、1回1,296バイトが上限。超えると例外が出て送られない。ログを見ないと気付かない。→ 上限に収まる数に分けて送る（NetMessageLimits）。
    PCが重いだけなのに「回線が混んでいる」と判断してしまった
    RTTにはフレームの長さが含まれる。一斉投入でFPSが下がると、LAN内でもRTTが1→20ms以上に延びた。→ RTTはならして使い、基準も早めに忘れる。判定の幅を広くとる。
    送る回数を減らしたら、むしろ悪くなった
    先読みの距離が延びて外れが増えた。→ 減らすなら「目に見えない細かさ」の方。
    小数の計算は全PCで同じになると思っていた
    CPUの命令（FMAなど）や最適化で最後の桁が変わり得る。差分や同じ計算を前提にする所は、整数にするか、照合して立て直せるようにする。
    同じフレームで「消す」と「出す」をしたら、両方消えた
    番号で消す仕組みが、同じ番号の新しい敵も消してしまった。→ 同じ写真で出直した敵は消さずに使う。
    受信した配列を、計算中のジョブが読んでいた
    受信は計算の途中でも起きる。→ 受信側の配列と計算用の配列を分け、計算が止まっている間に写す。
    配列のRPCや文字列でカクついた
    送受信のたびにゴミ（GC）が出ていた。→ 名前なしメッセージと一時メモリに。OnGUIの表示も確保の元。
    L13 / Quiz

    腕試し — 練習問題

    CHECK

    答えはクリックで開きます。全問説明できれば、このゲームの通信について一人前に議論できます。

    2万体を1体6バイト、1秒20回送ると、Client1人あたり何Mbps？
    20,000 × 6 × 20 ＝ 2,400,000 バイト/秒 ＝ 2.4MB/秒 ＝ 約19.2Mbps（× 8）。
    写真をUnreliableで送るとどうなる？
    1枚抜けると、次の差が「抜けた写真」を前提にしているので復元できない。毎回キーフレームを送るなら別だが、重くなる。だからReliableにしている。
    先読みを「2枚の間の補間」に変えると、何が良くなり何が悪くなる？
    外れ（瞬間移動）が無くなり、より安全になる。代わりに写真1〜2枚分（約0.03〜0.07秒）遅れて見える。
    位置の細かさを0.002から0.008にしても、ずれが溜まらないのはなぜ？
    Hostが「Clientが復元する位置（丸めた後）」を次の予想の元にしているから（閉ループ）。毎回の差はClientの手元の位置との差になり、誤差は半刻み以内に収まる。
    回線が混んで写真が遅れるとき、枚数を減らすのがダメなのはなぜ？
    写真の間隔が延びると、先読みする時間も延びて外れが大きくなる。特に動きが不規則な場面で悪化する。細かさを粗くすれば、間隔を保ったまま軽くできる。
    Clientの時計の差を「平均」ではなく「最小」で推定するのはなぜ？
    届くまでの時間はいつもプラスでばらつく。最小値が一番余計な遅れが少なく、本当の時計の差に近い。平均だとばらつきの分ずれ、揺れも表示に出る。
    このゲームでロックステップを選ばなかった理由は？
    3万体の押し合いはカオスで、PCごとのわずかな小数の計算の違いがすぐ大きなずれに育つ。全PCを同じ機種にできる保証がない。
    Glossary

    用語集

    Host ホスト
    部屋を立てたPC。サーバー役も兼ね、全ての結果を決める（権威）。
    Client クライアント
    Hostに参加するPC。Hostの結果を受け取って表示する。
    権威 Authority
    どの結果を正しいとするかを決める役。このゲームはHost。
    パケット
    データの小包。約1,500バイト以内（MTU）。
    MTU
    1個のパケットに入る最大の大きさ。Unity Transportでは1,400バイトを使う。
    帯域
    1秒に運べる量。Mbps（ビット）で言うことが多い。1MB/秒＝8Mbps。
    遅延 / RTT
    届くまでの時間 / 往復の時間。RTTにはPCの処理待ちも含まれる。
    ジッター
    遅延のばらつき。
    Reliable / Unreliable
    確実に（再送・順番どおり）送る / 届かなくてよい送り方。
    ACK
    「受け取りました」の返事。来なければ再送する。
    送信窓
    返事を待たずに先に送ってよい数。Unity Transportは64パケット。
    スナップショット 写真
    ある瞬間の状態を丸ごと記録したもの。
    キーフレーム
    差ではなく全部を入れた写真。途中参加・立て直しの出発点。
    差分 / 予測符号化
    予想との違いだけを送ること。
    量子化
    小数を決まった刻みの整数にすること。刻みより細かい情報は捨てる。
    ZigZag
    0,−1,1,−2,2… を 0,1,2,3,4… に並べ替え、マイナスも小さい数のまま扱う変換。
    指数ゴロム符号
    小さい数ほど短い可変長の符号。次数kで長さの配分を変えられる。
    チェックサム
    中身から計算する確かめ用の値。送り手と受け手で比べて壊れを見つける。
    補間 / 外挿
    2点の間を埋める（遅れる）/ 最後の点から先を予想する（外れる）。
    推測航法 Dead Reckoning
    最後に分かった位置と速度から今の位置を推定すること。
    ロックステップ
    入力だけを送り、全PCが同じ計算をする方式。計算が完全に同じである必要がある。
    GC
    C#が使い終わったメモリを集める処理。走ると一瞬止まる。
    Burst / Jobs
    Unityの高速・並列計算の仕組み。
    瞬間移動 snap
    先読みの外れが大きすぎ（2以上）、滑らかにせずその場で合わせたこと。

    // 前の2枚(h1=直前、h2=その前)から、今回の位置を予想する(整数のみ)。ratioQ = 間隔の比 × 1024
public static int2 Predict(int2 h1, int2 h2, int ratioQ)
{
    var delta = h1 - h2;
    return h1 + ((delta * ratioQ + 512) >> 10);
}
    // 差を 2^shift 単位に丸める(四捨五入。負の数もシフトだけで計算し、HostとClientで必ず一致させる)。
public static int QuantizeResidual(int residual, int shift)
{
    return (residual + ((1 << shift) >> 1)) >> shift;
}

// 予想に丸めた差を足して位置を戻す。Hostもこの値を次の予想の元にする(誤差が溜まらない)。
public static int2 Reconstruct(int2 predicted, int2 quantizedResidual, int shift)
{
    return math.clamp(predicted + (quantizedResidual << shift), short.MinValue, short.MaxValue);
}
    // k次の指数ゴロム符号: (n-k)個の0、1、続いて w=value+2^k の下位nビット(nはwの最上位ビットの位置)。
// ビットは下位から詰める(LSB-first)。読み手は0の数を数えて長さを知る。
public void WriteExpGolomb(uint value, int k)
{
    var w = (ulong)value + (1UL << k);
    var n = 63 - math.lzcnt(w);
    Write(0u, n - k);
    Write(1u, 1);
    Write((uint)(w & ((1UL << n) - 1UL)), n);
}
