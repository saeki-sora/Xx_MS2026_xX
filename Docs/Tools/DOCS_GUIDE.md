# Tool docs — how to write and maintain them

Rules for every agent (and human) touching `Docs/Tools/`. Referenced from `CLAUDE.md`.

## 1. What exists
Each tool has **two docs**, both kept in sync with the code:
| Tool | Human guide (planner-friendly HTML) | AI reference (Claude Code) | Code |
|---|---|---|---|
| 要塞デザイナー / Fortress Designer | `FortressDesigner_ガイド.html` | `FortressDesigner_AI_Reference.md` | `Assets/_Game/Fortress/` |
| 握力入力ブリッジ / Grip Input Bridge | `GripInputBridge_ガイド.html` | `GripInputBridge_AI_Reference.md` | `Assets/_Tools/GripInputBridge/`, `Assets/ArduinoSerialReader.cs` |
| ShaderFX | `ShaderFX_ガイド.html` | `ShaderFX_AI_Reference.md` | `Packages/com.ms2026.shaderfx/` |
| SpriteAnim | `SpriteAnim_ガイド.html` | `SpriteAnim_AI_Reference.md` | `Packages/com.ms2026.spriteanim/` |
| D-Drive (3rd-party, `com.ddrive.core`) | `D-Drive_ガイド.html` | `DDrive_AI_Reference.md` | `Library/PackageCache/com.ddrive.core@*` + `Assets/_Game/DDrive/` |
Hub: `index.html` (tool cards + 「どれを使う？」 list). Shared assets: `assets/guide.css`, `assets/guide.js`. Older design specs (`GripInputBridge_設計仕様書*.md`) are intent documents, not maintained references.

## 2. When to update (same task as the code change — not later)
- Any change to a tool's behaviour, UI labels, menus, tabs, buttons, default values, file paths, public API, data fields, or known limitations.
- New tool → create both docs from the closest existing pair, add a card + 「どれを使う？」 rows to `index.html`, add a row to the table above and to `CLAUDE.md`.
- D-Drive: version bump (`Packages/manifest.json`), new/renamed IDs in `Assets/_Game/DDrive/Generated/AssetIds.g.cs`, new D-Drive call sites, bootstrap/settings changes.
- Removing a feature → remove it from both docs (don't leave stale recipes).
- Also bump the date stamps (`2026-10-03 時点` in HTML side nav/footer, "Verified … on" line in the .md).

## 3. Human guide (HTML) rules
**Audience: a planner who has never opened the tool.** If a sentence needs programming knowledge, it belongs in the developer zone.

Page order (keep it):
1. Hero — `oneword` (what it is in one sentence, with `.hl` highlights), `analogy` (everyday metaphor), `facts` (誰が使う / 開き方 / 必要なもの / 今の状況).
2. 何ができる？ — feature cards (`.cards` + `.card.feat`, each with an `.ex` concrete game example) or a `.flow` diagram.
3. はじめての 5 分 — `.steps` with numbered `.step`; use `.step-body` + `.mock` for faithful UI mock-ups; end with `.done`.
4. やりたいこと逆引き — `.recipe` `<details>` with `data-tags` matching `#recipeChips` filters; `#recipeSearch` input; end list with `.noresult`.
5. 画面の見かた — `.tabguide` (one `.tg-panel` per tab/screen, `.when` line + `ul.points`).
6. 数値の意味 — `.ptable-wrap` tables: 項目 / 何が変わる / 上げると / 下げると / 初期値.
7. 困ったとき — `.faq` details.
8. 用語集 — `dl.gloss`.
9. `<div class="devzone"></div>` then developer sections with `data-dev` (code tabs `.tabs`/`.panel`/`.codebox`, `.notes`).
10. 関連ツール — `.links` + `footer`.

Writing rules:
- Plain Japanese, short sentences. Explain every term the first time or link it in 用語集 (or `<span class="term" tabindex="0" data-tip="…">`).
- Quote UI exactly as it appears in Unity: button/field names in `<b>…</b>`, menu paths as `<span class="mp">Tools<i>›</i>要塞<i>›</i>…</span>`, keys as `<kbd>`. **Copy labels from the source code**, never paraphrase a label.
- Give numbers with their defaults and a concrete consequence ("全力で約 10 秒でオーバーヒート").
- State current limitations honestly in `.callout.warn` (e.g. "今の仕様の注意").
- Only claim what you verified in code. No marketing.
- Sections need `id` + `data-nav="目次ラベル"`; the side nav is generated by `guide.js`.
- Per-page accent colours: set `--acc --acc-ink --acc2 --acc3` in a page `<style>` for both `:root` and `:root[data-theme="light"]` (light values must be dark enough for contrast). Existing: Fortress cyan, Grip red, ShaderFX violet, SpriteAnim orange, D-Drive lime.
- Inline page-specific CSS/JS is fine; shared components go into `assets/guide.css` / `guide.js` (keep them dependency-free; wrap storage access in try/catch).
- Code in `<pre>` inside `.codebox`: escape `<`/`>` as `&lt;`/`&gt;`; add `data-plain` on the `.codebox` to skip highlighting.

Verification before finishing:
- Serve over HTTP — `python -m http.server 8765 --directory Docs/Tools` (also the `tool-docs` entry in `.claude/launch.json`) — because file previews that inline the page can't load the relative `assets/` CSS/JS.
- Check at ~390 px width: no horizontal overflow outside tables/code, no console errors, side nav lists all sections, recipes filter works.

## 4. AI reference (.md) rules
- Audience: Claude Code with zero context; goal: answer without opening the source. English prose (token-efficient), Japanese only for exact UI labels/menu paths.
- Header: purpose, "Verified against source on <date>", link to the HTML guide, maintenance rule.
- Sections (adapt): 0 Mental model · 1 Paths/asmdefs/assets in this project · 2 Public API (signatures) · 3 Data assets (fields + defaults) · 4 Editor UI (exact labels, menus) · 5 Integration with other tools/game · 6 Gotchas (implementation gaps, footguns) · 7 Related.
- Separate "implemented" from "design intent". Record known gaps as gotchas instead of silently fixing them.
- Prefer tables and signatures over prose. Keep it under ~40 KB.
- Extraction tip: when scraping fields with regex, include lines with inline attributes (`[Range(..)] public float X`).
